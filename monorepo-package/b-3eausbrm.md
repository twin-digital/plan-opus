# The bundler is not an exception a package may opt out of

`r-82ck2fax` says a package's shared configuration is generated by the monorepo's config manager,
and that "an exception for one package is declared where that configuration lives." That sentence
is doing more work than it should. It reads as a general escape hatch: any generated rule may be
switched off in `.repo-kit.yml` so long as the switch is declared there.

Some of those rules genuinely are per-package taste — which subpath exports a package publishes,
what its test timeouts are. **Building through the monorepo's bundler is not.** A package that
opts out of `bundle` stops being built the way every other package is built, and the opt-out looks
identical in the config to the ones that are fine.

What I want the preset to carry is a requirement that a package builds through the monorepo's
bundler, full stop — so that `bundle: false` is not an exception an implementer may take, and a
package the bundler does not suit is an escalation to the owner rather than a line in
`.repo-kit.yml`.

This came out of the mc-dev-kit 009 build. The kit gained `tsdown` as a devDependency for the
types its exported build fragment names; repo-kit's `bundle` rule keys on that dependency, so the
next sync would have generated a `tsdown.config.ts` and switched the package off its tsc build.
The implementer reported it, and I took the opt-out — wrongly. The right move was to escalate, and
the reason I did not is that `r-82ck2fax` reads as though the opt-out were sanctioned.

Worth settling while designing this: whether the general "an exception is declared where the
configuration lives" clause should stay at all, or whether each generated rule should say for
itself whether it is optional — the current shape gives an agent no way to tell a taste rule from
a load-bearing one. And whether "the bundler" wants naming in the requirement or should stay
tool-agnostic, as `r-82ck2fax` does today.
