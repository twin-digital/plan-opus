# Minecraft dev kit: Design Brief

The dev kit is the library that answers, for a workspace of Minecraft Bedrock packages, *which packs exist here and what is each one*. It finds the packs, parses and validates their manifests, classifies each pack's kind, and hands back a normalised pack set — one entry per pack, carrying identity, version, kind, the directory holding the pack, and the package that owns it. Everything about running a server sits on top of it: the dev harness (`minecraft/dev-workflow`) consumes the pack set and owns deployment, activation, reload, watching, and the selection UX. The kit's defensible core is identify, validate, normalise; it may orchestrate or configure a build, but how a package assembles its built output stays the package's own business.

It exists because the harness design could not resolve two tensions from inside itself. First, source layout serves two masters: pinning packs to a fixed path so *discovery* can find them also dictates the input to *build*, so a package cannot reorganise its sources without breaking discovery. Second, auto-detecting every pack in the workspace answers *what exists*, while running a test server against part of a monorepo asks *what do I want right now* — a selection is an argument, not a roster that drifts. Both point past the harness at a general kit, with dev hosting as one consumer.

This branch explores one shape: **each package declares its own packs**, next to the code it describes — which packs it contains, where each pack's sources live, and where each pack's built output lands. The kit owns that declaration's schema and validates it. The declaration is deliberately narrow, stating only what the manifest cannot: identity and kind come from `manifest.json` and are never restated, because two declarations that can disagree recreate a failure the server reports as nothing at all. What the shape buys is enumeration without a build — a clean-checkout listing, a bare validate, and a source typo that surfaces at discovery instead of as "no packs found" after a build. What it costs is per-package boilerplate and a declaration that can drift from what the build actually produces. The mirror-image shape — locating packs by scanning built output, no declarations and no drift, but nothing enumerable until a build has run — is explored on a sibling branch; the owner picks between them, and this branch is abandoned rather than merged if the other wins.

The inputs here are captured for that shape and deliberately stop short of designing it. Left open for the design: the pack-set data structure and the verbs over it; where a declaration lives (a `package.json` field, an exported descriptor, a file) and whether the surrounding tooling tolerates it — a fact to establish, not a preference to assert; how a stated output location is checked against what the build produced; the validation rules and error surfaces beyond the outcome the requirements decree; and how a build maps to the packs it changed, for watch.

## What is still open

Six matters are the owner's to decree, and none is answered here.

1. **One design or two**, and whether kit and harness ship as one package or separately.
2. **Whether packages declare their packs explicitly, or membership is inferred** — the fork this branch and its sibling exist to price. Everything captured here assumes the declared answer; if the owner decrees inference, these inputs go with the branch.
3. **Whether the kit serves non-dev consumers** (release, CI). This decides whether it is a product or an extraction from the harness.
4. **Selection semantics** — whether the default is all packs, whether profiles persist, and whether a selection can name worlds or server versions too. The drafted requirement says only that a selection filters and never redefines what exists.
5. **Whether resource packs move from optional to required** — that turns kind-handling from a filter into a router with two pools and two world lists.
6. **What a *package* is** — the versioning fork left open by `design/minecraft/dev-workflow/artifacts/pack-layout/ADDENDUM.md`: whether packs sharing a package may share a version and a release artifact, or every pack is its own package. It matters more once a kit implies a release path.

Two further matters follow from the shape rather than from the owner's taste. `r:pack-source-layout-is-fixed`, a live requirement of `minecraft/dev-workflow`, is contradicted by any shape where a package states where its own sources are; adopting this shape means retiring it, which is the owner's call. And the migration is real: no package in the existing workspace carries a declaration today, so until each pack is edited, nothing is discoverable.
