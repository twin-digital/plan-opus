# Minecraft dev kit: Design Brief

The dev kit is the library that answers, for a workspace of Minecraft Bedrock packages, *which packs exist here and what is each one*. It finds the packs, parses and validates their manifests, classifies each pack's kind, and hands back a normalised pack set — one entry per pack, carrying identity, version, kind, the directory holding the pack, and the package that owns it. Everything about running a server sits on top of it: the dev server harness (`minecraft/dev-server`) consumes the pack set and owns deployment, activation, reload, watching, and the selection UX. The kit's defensible core is identify, validate, normalise; it may orchestrate or configure a build, but how a package assembles its built output stays the package's own business.

It exists because the harness design could not resolve two tensions from inside itself. First, source layout serves two masters: pinning packs to a fixed path so *discovery* can find them also dictates the input to *build*, so a package cannot reorganise its sources without breaking discovery. Second, auto-detecting every pack in the workspace answers *what exists*, while running a test server against part of a monorepo asks *what do I want right now* — a selection is an argument, not a roster that drifts. Both point past the harness at a general kit, with dev hosting as one consumer.

The shape is membership by convention. A workspace package carries at most one behavior pack and at most one resource pack — the shape the whole ecosystem models, and the shape that makes an addon — and it is a pack-bearing package exactly when its *source* holds `behavior_pack/manifest.json` or `resource_pack/manifest.json`. Nothing is declared: no marker field, no registry, no config entry. Built output is assumed to be `dist/`, with a way for a package to say otherwise. Because membership is known from source before any build runs, the kit enumerates packs on a clean checkout, and a missing or misplaced build output is already a loud error naming the package and the path it looked in — which is why neither a build-emitted report of what was produced nor a resolver shared between the build and the harness is needed: both existed only to detect that drift. Identity and kind still come from the manifest alone; the kind-named directory locates a pack and never overrules it, and a directory whose manifest disagrees with it is an error rather than a preference the kit resolves quietly, because a pack misfiled between kinds fails silently at the server and nothing downstream reports it.

Two other shapes were weighed and dropped, and the reasons still bound this one. A **config-first registry** — a file declaring each pack's source root, kind, and output — fails as a registry: the ecosystem standard it would model keys `packs` by pack *type* with one path each, so a second pack of a kind has nowhere to go, and inventing a house registry instead recreates a duplicate-declaration failure, where a config saying `behaviorPack` and a manifest whose modules say `resources` disagree with nothing detecting it and the server failing in silence. A config file is the right home for *what I want right now* and the wrong home for *what exists*. A **build-tool plugin** fails on the same evidence from the other end: the one ecosystem build integration that exists hard-codes a single pool path per project and merges every listed source folder into one pack, so it is structurally single-pack. The insight worth keeping from it is that the build knows its own outputs; the coupling is not.

The inputs stop short of designing. Left open for the design: the pack-set data structure and the verbs over it; how a package specifies an alternate output location, which the owner deliberately did not fix; the validation rules and error surfaces beyond the outcome the requirements decree; and how a build maps to the packs it changed, for watch.

## What is still open

Owner decisions have settled how membership is determined, how many packs a package holds, and where built output is looked for. What remains for the owner:

1. **One design or two**, and whether kit and harness ship as one package or separately.
2. **Whether the kit serves non-dev consumers** (release, CI). Archive packaging is a release surface — the dev loop deploys pack directories into server pools and never builds an archive — so whether the kit owns `.mcpack` and `.mcaddon` emission is a boundary worth watching rather than an obvious yes.
3. **Selection semantics** — whether a selection can name worlds or server versions as well as packs. That a selection defaults to all discovered packs, and that a persisted profile is a saved argument rather than a source of truth, is settled on the dev-server side; whether the kit models any of it, or leaves selection entirely to consumers, is not.
4. **How an alternate built-output location is specified.** The owner has no fiat answer; the mechanism is genuinely undecided, and no requirement fixes its shape.
5. **Whether the dev server deploys resource packs.** Discovering both kinds is settled; deploying them is not, and it is not a small increment: the two kinds have separate pools and separate world activation lists, and a pack misfiled between them fails silently at the server (`pack-kind-mismatch-fails-silently-at-the-server`). This puts pressure on the area-scoped `behavior-packs-required-other-content-optional`, which the owner may want to reword.
6. **What a *package* is, for versioning.** One package holding a behavior pack and its resource pack means the two share a version, a changeset, and a release artifact. That follows from the scope decision rather than standing on its own, but it is the fork `design/minecraft/artifacts/pack-layout/ADDENDUM.md` raised, and it matters more once a kit implies a release path.
7. **A stale clause in an elevated requirement.** `built-output-assembly-is-the-package-s-concern` ends "Only the source layout is fixed." It was written when `pack-source-layout-is-fixed` pinned packs at `pack/manifest.json` or `packs/<name>/manifest.json`; that requirement is now retired, and what fixes a source location is `membership-from-source-manifest-presence`. The statement is carried verbatim rather than reworded, because the wording is the owner's. It reads as intended under the new membership rule, but the owner may want the clause restated.

The migration is real: no package in the existing workspace sits at this source layout today.

One matter is deliberately not rested on. A single-pack `.mcaddon` is structurally legal by the first-party definition, but no first-party source says a client imports one (`release-archives-follow-pack-content` carries the caveat); emitting by content avoids the case entirely, and any design that would rely on it must establish it by test first.
