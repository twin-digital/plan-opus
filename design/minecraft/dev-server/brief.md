# Minecraft dev server: Design Brief

The dev server is the harness a pack author runs to iterate on Bedrock behavior packs against a real, disposable server. The daily feel it should produce: one command brings up a server and starts watching; you edit a pack's source, save, and the change is live in-game within a second or two without kicking anyone; you close the loop and the server keeps running so you can reattach. It is a developer-experience tool — nothing it does is shipped, and its only job is to make the edit→see cycle short and the throwaway cost low.

It exists because Bedrock offers no native hot-reload path for a monorepo of packs: a pack must be copied into the server's `development_behavior_packs` pool, *activated* by a separate per-world list that is only read at world load, and then `/reload`ed — and the pieces have sharply different refresh semantics. Script and function edits reload live; a pack newly added to the pool, or a change to the activation list, needs a server restart. A prototype wired all of this end-to-end and, through several review rounds, learned where the sharp edges are.

The design is the server half of that harness, and only that half. `minecraft/dev-kit` owns discovery, identification, and build: it answers which packs the workspace holds and hands back a validated pack set carrying each pack's identity, version, kind, directory, and owning package. This design consumes that set and owns everything downstream — the Compose project and volumes, readiness, pool routing by kind, activation lists, reconcile and diff, reload-versus-restart, watch orchestration, interleaved output, and the selection UX. That boundary is what narrowed the design: the pack side of what the old harness specified is gone, and the server side stands.

Two things follow from selection. Discovery answers *what exists* and forbids a hand-maintained list of it; which of the discovered packs a given run hosts is an argument, defaulting to all, and a persisted profile is a saved argument rather than a second source of truth. Because reconcile now matches the *selected* packs rather than the whole built output, deselecting a pack is a removal — and a removal changes the world's activation list, which the server reads only at world load, so it costs a restart.

## What is still open

1. **The dependency on `minecraft/dev-kit` is not yet citable.** This design rests on the kit's pack set, and under this repository's rules a cross-design dependency is a fact sourced by verbatim quote to the upstream design's published interface. The kit has no `spec.md` yet, so no such quote exists and none is invented here. Once it does, the fact this design needs must quote two things: the fields of a pack-set entry, and the guarantee that every entry names a directory whose root holds a `manifest.json` with a header uuid unique within the set. Until then the dependency is stated in prose and nowhere else.
2. **Whether the harness deploys resource packs.** The area-scoped `behavior-packs-required-other-content-optional` makes it optional. It is not a small increment: the two kinds have separate pools and separate world activation lists, and a pack misfiled between them fails silently at the server (`pack-kind-mismatch-fails-silently-at-the-server`), so supporting both turns kind-handling from a filter into a router.
3. **What `/reload all` is worth.** The prototype only ever issued a bare `reload`. Microsoft documents `all` as reloading whole behavior and resource packs rather than just function and script files, at the cost of making players quit and rejoin. That is a middle option between a live reload and a container restart, and whether it collapses any of the restart cases is untested.
4. **Which changes beyond a new pack and an activation-list edit force a restart.** What was observed is that scripts reload live and those two do not. Microsoft's content-type table documents block, entity and item definitions as only *partially* hot-reloadable and manifest changes as needing the world exited and re-entered, but says nothing about a renamed pack folder, and its remedies are world-scoped rather than server-scoped. The exact restart classification the harness needs is not yet established by evidence.
5. **Selection ergonomics** — how a selection is named on the command line, and where a persisted profile lives.
