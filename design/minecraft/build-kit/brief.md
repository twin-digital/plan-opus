# Minecraft build kit: Design Brief

Every package in the Minecraft Bedrock monorepo needs the same build: bundle its script module, put every other file the pack is made of into the output tree, get its manifests written out complete, and — for a release — archive the result. That work has no owner today. Each package carries its own build wiring, so the output layout and the completion rules are copied into every package that wants a loadable pack, and a package that copies them slightly wrong ships output that fails at the server with nothing reporting why. This design owns that build.

It ships inside the same package as `minecraft/dev-kit`. One distributable, two designs: the kit's side reads a workspace, validates it, normalises it into a pack set, and fills in the values a source manifest deliberately leaves out; this side turns a package's source into the built tree those values land in. The kit's half is settled and built, so what this design rests on is now recorded rather than awaited: it completes the manifests, it reports where each pack's built output is expected, and it produces none of that output itself — `f:dev-kit-reports-a-fixed-kind-named-output-location-and-writes-none`, alongside the entry details `f:dev-kit-pack-set-entry-names-package-kind-source-and-identity` already carries. The split is a split of subject matter, not of artifacts — a design boundary and a package boundary are not obliged to coincide, and nothing here is a reason to publish two packages. `minecraft/dev-server` remains the third party, owning watching at the workspace level, deploying into a server pool, activating, and reloading.

The form it takes is a configuration fragment, not a tool. The repository already has a build convention: a shared bundler base config, per-package overrides as shallow-merged fragments beside the generated `tsdown.config.ts`, a generic `build`/`watch` pair that picks a strategy by which config files are present and shells out to the tool's own CLI, and `repo-kit` generating the per-package snippet from a declarative rule. So the kit's package exports a fragment factory for the canonical bundler, `repo-kit` writes the snippet into any package that depends on the kit, and the existing detection then runs the bundler in build and in watch. No new command, no bundler pulled into this package, and no change to the generic tooling.

What that fragment covers is wider than bundling. The script module is bundled with the game-provided modules left external, but a pack is mostly not TypeScript — functions, entity and item definitions, textures, `.lang` files — and all of it has to reach the output tree or the built pack is not loadable. Those files, and `package.json`, are imported by nothing, so a module graph will never notice them changing; they have to be declared inputs, or an asset edit and a version bump rebuild nothing. That splits rebuilds in two: a source change that rebundles, and a version or manifest-input change that only brings the completed manifests up to date. Assembly also has to be authoritative over the output tree rather than additive, because a copy-only build leaves a file deleted in source sitting in the output, where it ships in the archive. Release then falls out of the same path: versions come from `package.json`, so a release is a version bump, a build, and an archive of the output tree.

## What the design must still decide

- **Whether the build still ships inside the kit's package.** This was drafted while the kit was a draft. The kit has since shipped: `@twin-digital/mc-dev-kit` is a discovery library whose four runtime dependencies are the three workspace-enumeration packages it delegates to and `semver`. Putting a bundler config fragment and a repo-kit feature into that same distributable now has a price that did not exist when the requirement was written, since a library a consumer imports to read a workspace would begin carrying build tooling. `r:build-ships-in-the-kit-package` stands as drafted and is the owner's to accept with that in view; the design's name follows whichever way it goes.
- **A package holding two packs.** The kit fixes the shape: a package structurally holds at most one pack of each kind, and each reported pack carries its own output location, so two packs means two entries and two output trees. What is open is this side — one bundler config across both trees, when only the behavior pack has a script module at all.
- **Where manifest completion runs** — as a hook in the bundler's own lifecycle, or as a step beside it. The manifest-only rebuild path hangs on the same answer.
- **How the extra watch inputs are declared.** The option is to be confirmed against the installed bundler rather than guessed at here.
- **What triggers the repo-kit feature.** Depending on the kit is the obvious condition; whether it is the right one, and whether anything else has to hold, is open.
- **Where the seam with the kit's own design falls.** The draft decision this bullet used to name is not in the settled kit, which instead excludes producing or deploying built output outright and never reads the output tree it reports. So the kit calls no build and the seam is one-way. What is open is the other direction: whether this side reads the pack set at build time at all, or works from the package it is generated into and leaves the set to the consumers downstream.
- **What a rebuild reports.** A watching consumer needs to know which packs a rebuild changed before it can redeploy them; nothing here fixes how it learns that.
- **Whether a non-default output root is needed at all.** The kit settled this by not having one: an output location is computed from the package directory and the kind and is never probed, so there is nowhere for a package to state its own. If this design needs one, that is a change to the kit rather than an open question here.
- **This design's name.** `build-kit` reads as a second kit, which is now exactly what it is not — `pack-build` or similar may fit better. This follows the packaging decision above.
