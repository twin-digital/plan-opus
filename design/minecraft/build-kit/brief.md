# Minecraft build kit: Design Brief

Every package in the Minecraft Bedrock monorepo needs the same build: bundle its script module, put its pack source under the output root, get its manifests written out complete, and — for a release — archive the result. That work has no owner today. Each package carries its own build script, so the output layout and the manifest-completion rules are copied into every package that wants a loadable pack, and a package that copies them slightly wrong produces output that fails at the server with nothing reporting why. This design owns the build: one implementation every package invokes, so those rules live in one place and a built pack cannot be produced without them.

It sits between two siblings. `minecraft/dev-kit` is the library that discovers the packs in a workspace, validates them, normalises them into a pack set, and fills in the values a source manifest deliberately leaves out; it reads and computes and touches no files. `minecraft/dev-server` owns watching, deploying into a server pool, activating, and reloading. This design is what turns a package's source into the tree those two talk about — it does the I/O and runs the toolchain (a bundler, an archiver), and calls the kit for everything about manifests.

The shape the conversation landed on, offered to the design rather than imposed on it: a separate package layered on the kit, so a consumer that only wants to know what packs exist does not pull in a bundler; one implementation behind both a command (what a package's `build` script runs) and a programmatic call (what a watch loop runs per changed package); a build that covers one package, leaving ordering and caching to the workspace task runner; and no configuration for a package that follows the conventional layout, since the source and output layouts are already fixed. Release then falls out of the same path: versions come from `package.json`, so a release is a version bump, a build, and an archive of the output tree.

## What the design must still decide

- **The kit's manifest completion is not published yet.** This design rests on the dev kit filling in `header.name`, `header.version`, and the version on a dependency naming an in-workspace pack, and on the fixed kind-named output layout those rules assume. That behaviour lives in an unmerged draft spec on another branch, so it cannot be sourced as a fact by repo-relative url and verbatim quote the way a cross-design dependency must be. Until the kit's spec lands on main, this design cannot record the dependency honestly and cannot settle.
- **Where the seam with the kit actually falls.** The kit's draft holds a decision that a package's own build script is invoked and the kit's completion pass runs over the output root afterwards. This design proposes to own that build instead, which is the same seam read the other way round. Which side calls which is the design's to settle with the kit's, not a thing the inputs fix.
- **Whether a package needs configuration beyond the `minecraft` key.** The requirement fixes where a setting goes; whether anything beyond an output-root override is needed at all is open.
- **How script bundling is configured** — bundler, entry point, what stays external, and how much of that a package may vary.
- **Whether watching belongs here.** Either this tool watches, or it exposes the rebuild call and `minecraft/dev-server` keeps the watch loop. Both were live; neither was chosen. Bound up with it: what a rebuild reports back about which packs it changed, which is what a watcher needs to know what to redeploy.
- **The command-line surface** — the subcommand names, the arguments, and whether archiving is a separate command from building.
- **The package's name**, and this design's own — `build-kit` reads close enough to `dev-kit` to be confusable.
- **Whether the archive-format evidence needs promoting.** The fact that a distribution archive follows what a package contains is held at `minecraft/dev-kit`'s own scope. If this design comes to rest on it, it is promoted to the area scope rather than reached across for.
